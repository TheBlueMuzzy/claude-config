# /develop — build the solution (diverge, then settle)

Steps are marked by how they happen (F80): ① a script or hook does it · ② Claude's judgement, refused or sent back until it's on record · ③ judgement only. Hooks: `~/.claude/config/bmuz/HOOKS.md`.

Read `~/.claude/config/bmuz/PROJECT-FILES.md` if you haven't this session ③ (reading). Old GSD layout? Offer the conversion first (session start flags it).

## 1. Line up
- No SPRINT.md (or it's finished) → do `/sprint` B (plan the next sprint), get OK, then continue here ③ (routing).
- Tiny request that isn't in the sprint ("shrink it to 93%") → just do it on the current branch, commit, done. Not everything needs a task ② (stop-plan-check asks for a task line or a one-line "tiny fix").
- Open `Ask Muzzy:` questions on the next task? Ask now (2–3 options + your pick), write answers into Notes ① listed at every session start (session-start.sh) · ③ asking well.
- **Branch — one work branch per delivery, not per sprint:** on the default branch (main/master) → create `dev/<milestone-slug>` and switch (if the project auto-deploys from main, say once: "The live site now only updates when you `/deliver`."). Already on a `dev/…` or other work branch → stay on it, across as many sprints as it takes until `/deliver` ② (guard-git refuses `F08:` code commits on main).
- **UI task?** Framework pieces behind the newest are named at session start ①; install/update any module with `node ~/.claude/config/bmuz/scripts/install-module.mjs <module> .` ① — it refuses a module whose own checks are red, shows the dry run, installs, then runs the game's checks for it.
- STATE (only if it changed): Stage = develop, Doing = "F08 — building" ③ (every sprint feature is 🔨 at once, so nothing can tell which one is in hand; the `F08: done` gate checks STATE).
- One-line kickoff: "Picking up F08 — hover lifts the card. 3 tasks left in this sprint."

## Focus rule (Muzzy asked to be kept on track)
- **One feature being built at a time.** If Muzzy starts steering to another feature, say so in one line and offer to park it ③ (conversation).
- Mid-feature reports are sorted out loud in one line: a tweak to *this* feature → do it · a bug → `/bug` triage (fix now only if P0, it breaks this feature, or it's a two-minute fix in code being changed — else log it and continue) · a new idea → ROADMAP → Ideas ③ (triage).
- **Every mid-sprint request becomes a SPRINT task line at once** (ticked when done), not just a Notes line — the planner (/ppp) only shows tasks (Goops sprint 05) ② (stop-plan-check sends a commit turn back while SPRINT.md is untouched; the planner republish too).
- Endless noodling on one feature → point it out kindly: "F08 has been in tuning for a while — ship it as is and log the rest as a ✨ feature?" ③ until F81 (producer notices: features stuck in 🔨/🎛️).

## 2. Do the tasks
For each unticked 🤖 task, in order (skip 🙋 tasks — remind Muzzy of them at the hand-off) ③ (order is judgement; the card's **Questions** is required ②):
- **Unattended runs** ("just go", overnight): **one fresh helper per feature.** Brief it with STATE RESUME HERE, the feature's SPRINT section and Key facts, and ask it to report what changed and anything surprising. The main chat only plans, merges, runs the Full check, reviews and saves. That keeps it small all night, instead of filling one chat to the 80% warning (F72) ③ (orchestration; the 80% nudge backs it).
- **Small tasks:** do them yourself. **Big ones** (lots of reading, or a fresh head helps): hand to a `general-purpose` subagent with the task, the feature's "Done when", relevant Key facts, and "report what changed and anything surprising." Tasks from different features that don't touch the same files can run in parallel ③.
- **Helpers' worktrees never get committed** ① (guard-git refuses a commit holding `.claude/worktrees/` until the ignore line is in .gitignore; save.mjs adds it) — they became embedded repos in Goops 2026-10-17.
- **After a helper's work is merged**, its finished workspace goes at the next save ① (save.mjs runs cleanup.sh — they were 3.9 GB in Glyphtender by v0.3.0).
- **Throwaway copies and proof shots** (yours or a helper's — say it in the brief) go in `~/Documents/dev/.scratch/<project>-<what>/` ① (guard-edits refuses a new folder or loose file straight in the home folder; cleanup.sh clears .scratch entries untouched for 24 h — 1 GB of copies piled up in ~/spike and ~/ppp-proof, 2026-10-19).
- **Helpers in worktrees** start from main, not the work branch: their brief's first step is `git merge --ff-only <work branch>`; tests, lint and git ignore `.claude/` (worktrees live there). Each helper's local servers use their own ports and storage (`wrangler dev --persist-to …`) ③ (brief content).
- **Helper briefs ask for the Area check, not Full** (PROJECT-FILES.md "Checks"): Fast + the e2e scripts for what they touched. Claude runs Full once after merging. A helper's report quotes its Area results; don't re-run them after a clean merge — run Fast ③ (brief content).
- **Layout/UI briefs list every size** — 390x844, 360x780, 844x390, a short window ~768x343, ~1100 wide, 1440x900, 1920x1080 — with per-size checks; a layout ask applies at ALL sizes **the game plays at**: a game whose `content/ui/style.json` says `"orientation": "portrait"` drops 844x390 + 768x343 (Goops — Muzzy: "not expected to function in horizontal/landscape mode. ever."), `"landscape"` drops the upright phones; copy that line into the brief. Look at a desktop shot yourself before saying done ② (check:framework checks UI at every size the orientation allows, F104; a visual change with no screenshot is sent back by handoff-check).
- **Breathing room is measured to what the player SEES** — the visible frame, art edge or border image, not the CSS box: a helper's "9 px inside the panel" was 1–2 px from Goops' angled dock art (framework sprint 22). Zoom the screenshot at the edge and say which edge you measured ③ (judgement; check:framework measures boxes only).
- **UI sprints / multi-part work — default pattern:** a framework helper ∥ a game helper when their files don't overlap; one bigger game helper per sprint, not one per task; bugs grouped by the files they touch (one helper per file group, not per bug). A Monitor on SPRINT.md ticks (and framework commits) posts the progress bar as tasks land — re-arm it when it expires ③ (orchestration).
- **Design is open** (feel, look, feature behaviour)? That's the diverge part — try 2–3 quick variants when cheap (behind a toggle or tuning value) and let Muzzy pick. Don't guess on taste ③.
- **"Feels off" / a `(tuning)` task** → think it through with **mda-analyze** diagnose before touching numbers: name the feeling → look at what players actually do (Dev Kit Snapshots/Time, bot runs, proto) → sort the cause (feel · readability · dynamic · the rule can't do it → /gdd) → offer 2–3 real knobs in `content/tuning/` with a prediction each, one at a time. Log `Tuning: knob old→new — why — result` in SPRINT Notes ③ (design thinking).
- Cause is **feel** (it works but feels flat, weak, floaty, no impact) → reach for **game-feel**: juice tiers in `content/feel.json`, still one knob at a time.
- Reach for specialists when a task calls for it ③: **proto** (rules/odds), **tuning-setup** (live sliders for tuning tasks), **save-system**, **audio-setup**, **multiplayer-setup**, **r3f-best-practices** + **three-best-practices** (any 3D work)… R3F rule: never React state for per-frame updates — mutate refs in useFrame ③ (until a lint rule exists — proposed).
- Any screen, menu, settings, HUD, dialog, results or lobby (or UI that looks off / breaks on a phone) → **game-ui**: it builds from the Game Framework UI kit in the game's chosen style. Never hand-style game UI ② (check-ui-edit tells Claude about kit-rule breaks in each src/ edit).
- Need placeholder art or audio? Follow the **placeholder ladder** in `~/.claude/references/indie-toolkit.md` (shapes → emoji/icons → Kenney/Quaternius kit → real art; ZzFX for sound), and log every asset we didn't make in `content/credits.json` ② (check:framework's credits check).
- A project needs Claude to work inside another program (Unity Editor, Supabase, a live Cloudflare deploy…)? Check `~/.claude/references/mcp-card.md` — prefer a CLI; offer the MCP in one line when its trigger hits, set up so it syncs (plugin or the repo's `.mcp.json`) ③ (rare).
- Features with rules or logic get **tests** as part of being done (rules/logic → unit tests; key flows → a Playwright smoke check). Feel isn't tested — Muzzy judges it ③ (what counts as "rules" is judgement; fixed P0/P1 bugs need `Guarded by:` — plan-lint).
- Tweakable values go into `content/` JSON (never hardcoded) so Muzzy can change them in the Dev Kit or Obsidian ③ (until a lint rule for numbers in game code — proposed). A new data file → it's named in the TDD ② (stop-plan-check sends the turn back until TDD.md mentions it or its folder). A new Dev Kit tool → TDD §1/§3 ③ until F92 (tech-lead routine: TDD kept true). A real "how should we build this" choice → TDD Decisions log ③.
- **A new tunable thing on screen** (a game with `content/devkit/select.json`, Dev Kit 0.14+) → put `data-knobs="<id>"` on what the player SEES and add its new knobs to that object in select.json — the game's select test fails until file and tags agree. **Every new tuning setting (rules too) goes on the object it affects** (Dev Kit 0.16+: `unlistedSettings` test; Muzzy can't add knobs himself any more — a click must show everything). A thing's parts (a glyphling's danger ring) carry the thing's tag, not their own. Place each setting by **where the code reads it and what changes on screen**, never by its name or label alone (Glyphtender audit 2026-10-14: 10 wrong + ~40 missing placements from label-guessing — the turn bar listed a pulse it never does; shared settings like player colours belong on every thing they colour) ② (the game's select / unlistedSettings tests in check:fast).
- **Tools, tests and sims read `content/`, never restate it** (Glyphtender F46: three scripts + the Dev Kit hard-coded "Large for 3–4 players", so the award re-tune measured the wrong board). Changing a default → grep for copies of the old value in `scripts/`, tests, e2e and tools, and re-measure anything that was measured on it ③ (code craft).
- **Changing a default players can save** (a New Game / lobby option): returning players keep their OLD saved value, so the new default never reaches them. With the saves module (framework F86) that's an **upgrade step**: `version` + 1 and `upgrades: { N: (old) => … }` dropping or resetting the field, so old saves take the new default once — plus a golden save of the old version with the new value in `expect` (Glyphtender v0.5.2, 2-letter words) ② (check:framework Saves fails until the new version has a golden save; the golden save's `expect` fails if the old value comes through). A game not on the saves module yet: version its save by hand the same way ③.
- **A random choice at game start** (turn order, first player, starting hand…) gets a fixed mode for scripted checks in the same task: browser e2e = `import.meta.env.DEV && navigator.webdriver` → fixed; server/unit tests = an explicit option. Otherwise e2e passes or fails by luck ③ (code craft).
- **Remaking a game: list every on-screen cue the old one had** (arrows, markers, glows, warnings) from its code and tick each off before calling a view feature done — Goops F14 missed v1's off-screen crack arrows until Muzzy noticed ③ (content audit).
- **Proving a test can fail (break the code on purpose): commit first** — `git checkout <file>` to undo the break also wipes uncommitted work (Goops F17 helper lost cracks.ts that way and had to rewrite it) ② (guard-git asks Muzzy before a checkout/restore that drops uncommitted work).
- **A test that got slow: find out why before raising its timeout.** Glyphtender 2026-10-08: client tests built their room server with the LIVE settings, so a clock jump fired the new idle takeover and the real AI played (26 s on GitHub → failed deploy); the fix was quiet test settings, and the timeout band-aid came out. A test that truly plays a whole game with the AI gets an explicit timeout (`}, 30_000)`) — the GitHub machine is ~2.5× slower than the PC ③ (debugging).
- **Enforced by hooks** ① (`~/.claude/config/bmuz/HOOKS.md` — the reasons are there): a type check before every commit · code with a backslash goes through Edit/Write, never a heredoc / `python -c` · a check's own exit code (no piping it into tail/grep) · no edits in a game's kit copy · no `F08:` code commits or merges on main · Python writes code files with `newline=''` (Windows CRLF, Glyphtender F71).
- **Framework code is linted and checked automatically (F70)** ①: lint-edit lints each file as it's edited (and says once per session when ESLint isn't installed yet → `npm install` there) · install-module refuses a module whose test, typecheck, check-ui or lint fails · GitHub re-runs them on every push.
- After each task: tick it in SPRINT.md, add surprises to Notes, commit `F08: <task>` ② (stop-plan-check sends a commit turn back while SPRINT.md is untouched). That's all — no STATE edits per task, no version.json (/save does that) ③.
- A feature's build tasks are done and it works → if it has `(tuning)` tasks left, set it 🎛️ tuning in ROADMAP (features that `~need` it can start now); else go to §4 ③ (judging "works").
- **Stuck** 3 times on one approach → stop, say so plainly, suggest another path (**systematic-debugging** method for real bugs). Found a bug too big to fix now → add it as a 🐞 feature in ROADMAP ③.

- **Every new system honours the module contracts** (`~/.claude/config/bmuz/MODULE-CONTRACTS.md`): reads `content/` through live hooks (Dev Kit edits apply while it runs — never only after a reload), keeps its timers on the rules clock (so both Dev Kit pauses stop it), and gives the adapter what it needs. Installing a module = wiring its hooks in the same task (Goops 2026-10-18: Dev Kit installed, nothing live — Muzzy: "the purpose of the devkit is to affect things live") ② (check:framework's live-tuning and pause checks).
- **Installing a module = proving its main promise in THIS game, end to end** (Dev Kit: move a Tuning slider → the running game changes; pause → it stops). A green install + green tests proved nothing in Goops (2026-10-18) ② (install-module runs the module's checks in the game) · ③ the end-to-end try.
- **Game hotkeys skip keys typed into a text box** (input / textarea / select / contenteditable) — otherwise the Dev Kit's search (or any name field) triggers game actions and loses letters (Goops 2026-10-18: "curve" → "cuv"). Dev Kit 0.17.1 also keeps its own keys inside ③ (code craft).

## 3. Prove it works (never "should work") — follow **verification-before-completion**: evidence before any "done"
- **Is the task really complete? — tests aren't enough** (Muzzy, 2026-10-14: "that kind of pass should have happened without my intervention… make sure the tasks are actually complete"). Before calling any big task done, re-read what it was meant to achieve and check the CONTENT first-hand, independently: every claim in the report traced to evidence (code, file, screenshot), not to what you meant to do. Hand-placed or hand-written content (a list, a mapping, copy, tuning) → audit it against the source of truth (a helper agent is fine) before reporting. Can't verify something → say so and ask, never present a guess as done. (Glyphtender sprint 29: Select lists placed by label-guessing were called complete; Muzzy's question triggered the audit that found 14 wrong + ~40 missing.) ③ (that IS the judgement).
- **Checks by tier** (PROJECT-FILES.md "Checks"): Fast after every task and merge ① (stop-check-fast runs it at every hand-back when code changed); **Full once per feature** after its merges (`npm run check:full` — side by side, ~10–15 min; link `e2e-shots/checks.html`), then record `Last full check: <commit>` in STATE ② (guard-git refuses `F08: done` without it). No `check:full` yet? Add it from `~/.claude/config/bmuz/templates/check-all.mjs` (give every e2e script its own port first); until then run e2e scripts one at a time. On GitHub with check:fast but no `.github/workflows/checks.yml`? Copy `~/.claude/config/bmuz/templates/checks.yml` there ② (checkup §7 names both; release.mjs refuses without GitHub green).
- **The AI acts like a person (F50 standard):** changing how a PLAYER's action looks or moves (a drag style, a landing, a speed) → change the same action for AI seats and online rivals in the same task, and test it (Glyphtender sprint 23 — Muzzy: "you forgot a rule") ③ (design rule).
- **Local servers stop with `node ~/.claude/config/bmuz/scripts/stop-servers.mjs <port|name>`** ① (guard-edits refuses taskkill / Stop-Process / kill-port and names it) — killing only what holds the port lets wrangler restart it (Glyphtender sprint 25, 4 leftover servers).
- **One check run at a time** ① (`check:full`, template 2026-10-18+, refuses a second run while one is going — Dev Kit e2e scripts reload every dev server mid-test, Glyphtender sprint 23; checkup §7 flags older copies).
- e2e / test craft ③ (too varied to check by code):
  - **A refused drag-and-drop must not run the TAP's side effects** (Glyphtender 2026-10-13: a seed dropped where it couldn't go fell through to "tap the ghost = undo the move", because the drop reused the tap handler). Give the handler a `dropped` flag and test a refused drop over every tappable thing ③.
  - **e2e finds an element by its own tag** (`[data-bot-draft]`), not "the first image in the layer" — a new sibling broke e2e:ai that way (Glyphtender sprint 23, F64's ghost preview).
  - **Parallel helpers share dev-server ports:** check what's listening before picking one and write the port in the script header; a CDP swipe must be quick (~10 ms a step) or it outlasts the game's swipe window; tap a slider "end" at 10%/90% of its track, not the edge (Goops F24) ③.
  - **Touch-emulated e2e:** in Chrome's touch emulation the first tap after a CDP touch drag loses its click (pointer + touch events arrive, no click) — tap a neutral spot once after each drag, and don't read that as a game bug without a real phone (Glyphtender sprint 27). An `aria-disabled` control needs `click({ force: true })` — Playwright waits for "enabled" (sprint 26).
  - **"What's on top here?" tests: `elementFromPoint` / `elementsFromPoint` skip `pointer-events: none`** — HUD words usually are, so an overlap/tap check looks straight through them; make everything hit-testable for that moment (framework F61: a crack count slid over the score passed until fixed — ui-kit `uiProblems.mjs` does it).
  - **e2e "can I press it?" = what's under its centre** (`el.contains(document.elementFromPoint(centre))`), not its box vs the container's — a clip mask hides an item whose box still "fits" (Glyphtender sprint 29: the Dev Kit's AI tab sat 0.4 px past a carousel page, the test called it in view and timed out; five scripts had copied that check).
  - **A tap that changes what's under the finger** (a panel that pops back, a menu that opens) waits ~350 ms before changing it — the tap's own trailing click lands after, on whatever appeared there (Glyphtender sprint 29: a phone pick re-picked a row of the panel that came back).
  - **Two sides, one test across them:** a game side and a server (or a writer and a reader, a CLI and a hook) built separately get a test that feeds one side's REAL output into the other's checker, and one shared helper for anything both must name the same way — framework F89: two helpers' sides each passed their own tests, yet a Date.now() moment, a day-old tab or an emoji made the server refuse the whole report, and the token file was named two ways. ③ (which sides must agree is design judgement; put it in the helpers' briefs up front)
- Visual change → start the dev server the way `/play` does (`--host`, the port from Key facts), open it in Playwright, screenshot, look at it yourself, fix, re-shoot. Fixes are commits too (`F08: fix …`) ② (handoff-check sends back a turn that changed src/**/*.tsx|css with no screenshot, unless **Proof** says "no visual change").
- Logic → play it via Playwright or a quick script; the console stays clean (a missing-favicon 404 doesn't count) ③ (check:fast + e2e cover part of it).
- Carry out the feature's `Check:` line, then write `Checked: <what you ran or looked at + the result>` under it ② (guard-git refuses `F08: done` without it).
- **Review the feature before showing it:** run `/code-review` (low) on the feature's commits only (`<start>..<end>` — a whole-branch diff is too big to read in one pass) and fix real bugs now — cheaper than finding them at /deliver; record `Reviewed through: <commit>` in STATE ② (guard-git refuses `F08: done` until this line, and `Last full check:` when the project has check:full, was updated during the feature — F75). (Not in the project's repo folder? Hand the review to a subagent working in the repo.) A feature that adds a **public server address** (a worker route, a room message, an upload) gets a **security** review too — limits under many requests at once, guessing, what's stored and who can read or delete it — and the helper's brief says so from the start (framework sprint 19: F96's link codes had 4 real holes after "done") ③ (judgement — what's public).
- Screenshots: also look for things **clipped inside boxes** (scroll areas, panels) — sideways-overflow checks don't catch those ② (ui-kit uiProblems in check:framework) · ③ your own look.

## 4. Hand to Muzzy (after each feature, or when he needs to look)
- **The hand-off card, every time** ② (`~/.claude/config/bmuz/templates/handoff.md` — Done · You'll see · Try it · Proof · Questions · Next `/command` — what it covers; handoff-check sends any other ending back after a work turn). The bullets below fill its sections.
- Describe what changed from the player's side (3–6 bullets) and what the screenshots showed (he can't see Playwright's images — describe them). Say exactly what to try ② (**You'll see** / **Proof** required).
- Feature has a `why:` line → end with its one feel question: "Did <moment> feel like <target, in players' words>?" Answer → SPRINT Notes ② (handoff-check sends back a card for a built feature with `why:` and no "Did … feel …?").
- List his 🙋 tasks and any new `Ask Muzzy:` questions ② (**Questions** required).
- **Links in the hand-off itself, not just "offer /play":** start the servers it needs (dev server `--host`, plus the online server if online is in it) and put the PC link, the phone (LAN IP) link and the checks results page in this message ② (handoff-check sends back a card whose localhost / LAN links don't answer). Autonomous runs too: the morning report ends with the links. Then wait.
- Feedback → fix → re-check → show again. **"Approved"** → feature ✅ done in ROADMAP (one approval covers its tuning too) ② (guard-git refuses `F08: done` until ROADMAP says ✅ or 🎛️), features that became 🟢 ready ① (plan-lint names them), replace STATE RESUME HERE + Doing ② (guard-git refuses `F08: done` without it), commit `F08: done`, then `/save` in the same turn and keep going in this chat ② (stop-plan-check sends the turn back while `F08: done` isn't pushed). Muzzy chose this on 2026-10-19: "save + keep going", so no `/clear` nudges.
- Sprint's features all done → first ask Muzzy for the 3-line retro (went well · went wrong · change; draft it from Notes if you like, his words win) and add it to SPRINT.md as `Retro:` ② (archive-sprint refuses without it). Then archive SPRINT.md (`node ~/.claude/config/bmuz/scripts/archive-sprint.mjs`, commits `Sprint NN done`), offering a **bug sweep** first when BUGS.md has open P0/P1 or several P2s ② (stop-plan-check sends the turn back with the open counts until it's archived). Report with the sprint header ② (handoff-check), then one line: "Sprint done. Next: `/sprint` for the next one" — or "`/deliver` — the milestone/alpha musts are complete" when true. (/deliver saves on its own.)

Main is merged only by `/deliver` ① (guard-git refuses a merge into main, merge.mjs and rollback.mjs outside /deliver).
